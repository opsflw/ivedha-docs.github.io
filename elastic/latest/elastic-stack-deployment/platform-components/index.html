    Platform components

    The platform release deploys twelve component applications. This page provides one customer-facing description and one stable documentation anchor for each application.

    The application identifiers are implementation identifiers, not Azure resource names. Do not use them to reconstruct resource IDs, hostnames, credentials, or other deployment-specific values. Obtain those values from deployment outputs.

    One-to-one component map

    Argo CD application Customer-facing purpose Availability
    computed-values Produces the approved configuration values consumed by the other component applications Every deployment
    deployment-postrequisites Completes release-defined configuration and readiness work after the main services are deployed Every deployment
    deployment-prerequisites Establishes release-defined dependencies and readiness gates required before the main services deploy Every deployment
    elastic-connectors Supplies supported Elastic connector services for approved external content or service integrations Plan, version, license, and configuration dependent
    elasticsearch Stores, indexes, searches, and analyzes customer data Every deployment
    fleet-server Coordinates enrolled Elastic Agents through Fleet Plan and configuration dependent
    infrastructure Supplies the shared Azure runtime, storage, identity, and networking foundation Every deployment
    ingress Presents approved HTTPS endpoints for enabled platform services Every deployment
    kibana Provides the browser interface for search, dashboards, administration, and enabled Elastic solutions Every deployment
    logstash Receives and processes events through configured input, filter, and output pipelines Plan and configuration dependent
    elastic-agent Runs the platform-managed Elastic Agent workload and its approved policy Release and configuration dependent
    secrets Supplies protected secret and certificate material required by platform services Every deployment

    A component listed as plan-dependent is not available merely because its Argo CD application exists in platform source. Confirm the deployed plan, version, license, status, and published endpoint before using it.

    Component descriptions

    Computed values

    Argo CD application: computed-values

    Computed values derives the shared, release-approved configuration consumed by other component applications. Its customer-facing result is consistent configuration across the deployment, including values later exposed through supported status and output views.

    Customers do not edit generated values or use this application as a source for resource names. Change deployment configuration only through a documented managed-application action.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-computed-values

    Deployment postrequisites

    Argo CD application: deployment-postrequisites

    Deployment postrequisites performs the release-defined configuration and readiness work that can run only after the main platform services are present. The exact tasks are version-specific; the customer-facing outcome is a platform that can advance from infrastructure deployment toward service readiness.

    Customers should follow the managed application's readiness state rather than attempting to run or modify individual post-deployment tasks.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-deployment-postrequisites

    Deployment prerequisites

    Argo CD application: deployment-prerequisites

    Deployment prerequisites establishes the release-defined dependencies and readiness gates required before Elasticsearch and the other main services can be configured. The customer-facing outcome is early validation of the foundation required by the selected plan.

    When this component does not become ready, review the managed application's status and deployment evidence. Do not bypass the gate by changing managed resources directly.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-deployment-prerequisites

    Elastic connectors

    Argo CD application: elastic-connectors

    Elastic connectors supplies the connector service used by supported Elastic workflows that synchronize content or interact with approved external systems. A deployed connector service does not automatically configure a data source, credential, synchronization job, or external model provider.

    Before use, verify the selected connector, Elastic version and license, outbound connectivity, credential owner, source permissions, and data classification. Elastic documents connector behavior in the Elasticsearch connectors reference.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-elastic-connectors

    Elasticsearch

    Argo CD application: elasticsearch

    Elasticsearch is the platform's distributed search and analytics engine, scalable data store, and vector database. It stores customer indices and data streams and provides APIs for indexing, search, aggregations, ingest pipelines, security, and supported lifecycle operations.

    Customers own mappings, templates, data streams, retention, API access, query behavior, and data governance. Use the deployment-provided Elasticsearch hostname rather than an internal Kubernetes or Azure address. See the official Elasticsearch reference.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-elasticsearch

    Fleet Server

    Argo CD application: fleet-server

    Fleet Server is the control-plane service through which enrolled Elastic Agents receive policies and report status to Fleet. Collected events are stored in Elasticsearch, not in Fleet Server.

    Use this component only when deployment outputs expose an approved Fleet endpoint. Customers remain responsible for their agent installations, source permissions, certificate trust, policy approval, and compatible versions. See Fleet and Elastic Agent.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-fleet-server

    Infrastructure

    Argo CD application: infrastructure

    Infrastructure supplies the shared Azure foundation consumed by the platform services. Depending on the approved release, that foundation can include the managed runtime, storage, identities, and networking resources represented in the managed resource group.

    The exact resource inventory is release-specific. Customers own the Azure subscription, policy, quota, approved connectivity, and Azure charges, but must not modify individual managed resources unless a documented action explicitly permits it.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-infrastructure

    Ingress

    Argo CD application: ingress

    Ingress presents the approved HTTPS routes for enabled services such as Elasticsearch, Kibana, Fleet Server, or Logstash. It connects the platform's internal service routing to the public or private access model selected for the deployment.

    Customers configure the required network path, DNS, TLS trust, and client access. The deployment-provided service hostname remains authoritative; do not connect clients to an internal load balancer, pod, or Kubernetes service name.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-ingress

    Kibana

    Argo CD application: kibana

    Kibana is the browser interface for exploring data, creating dashboards and visualizations, administering supported Elasticsearch features, managing access, and using enabled Elastic solutions.

    Kibana reads from and administers Elasticsearch; it is not a separate copy of the customer's indexed data. Customers use the deployment-provided Kibana hostname and receive only the privileges assigned to their identity.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-kibana

    Logstash

    Argo CD application: logstash

    Logstash receives, transforms, enriches, buffers, and routes events through configured input, filter, and output pipeline stages. It is useful when an ingestion flow needs processing beyond a direct Elasticsearch API or an approved agent integration.

    Use the managed Logstash service only when the selected plan publishes a supported endpoint and pipeline workflow. Customers own source behavior, pipeline requirements, parsing validation, credential rotation, and failure handling. See how Logstash works.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-logstash

    Elastic Agent

    Argo CD application: elastic-agent

    This application deploys the platform-managed Elastic Agent workload and its approved policy. Its purpose and enabled integrations depend on the platform release and configuration.

    This component is distinct from Elastic Agents that customers install on their own hosts or Kubernetes clusters. Customers operate those external agents and must verify Fleet enrollment, endpoint reachability, version compatibility, resource use, and source permissions.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-elastic-agent

    Secrets

    Argo CD application: secrets

    Secrets supplies the protected secret, key, and certificate material required by platform services and supported TLS or integration workflows. Secret values must not appear in deployment outputs, documentation, source control, or support evidence.

    Customers use only documented certificate, identity, or credential actions. Do not read, replace, or copy secret material directly from managed resources.

    Path and anchor: /elastic/latest/elastic-stack-deployment/platform-components/#component-secrets

    Verify a component

    For any component:

    1. Confirm that the component is included in the approved Marketplace plan.
    2. Check the managed application's platform version and readiness state.
    3. Use deployment outputs to find customer-facing endpoints or required actions.
    4. Confirm the Elastic version, license, and compatibility where applicable.
    5. Record the customer and iVedha ownership boundary.
    6. Treat the component as unavailable until all required evidence is present.

    For placement and data flow, see the architecture and deployment model. For customer and operator responsibilities, see shared responsibility.
